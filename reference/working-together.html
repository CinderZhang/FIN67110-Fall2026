Working together on GitHub: issue, pull request, merge

Your AI agent already knows how to run Git for you, though it cannot know what you want. These three words let you ask for it. Nothing on this page is required, because how your team works is your team's business. This page gives you the words, and your team may use them or not.

What the three words mean

Think of a research note your desk is about to publish. The published version is the one everyone trusts. In your repository that version is called main, and it is the copy a stranger runs. A branch is your own working copy beside it, where you can change things without touching what your teammates run.

Word What it means Research-note comparison
Issue a suggestion A comment in the margin. It is words only, so nothing in the repository changes. It has a number, people can reply to it, and someone closes it when it is settled.
Pull request (PR) new code or a new idea, proposed Your redraft handed over with the tracked changes showing. It carries the change itself, line by line, and teammates can read it and comment before it goes in.
Merge agreed and adopted The sign-off. The team accepts the pull request, and the change becomes part of main.

One simple test separates the first two: if you have only words, open an issue, and if you have the change itself, open a pull request.

When to use each one

You will use an issue when you want to point something out without changing any files yourself. A teammate might read one of your desk's reports and see that the diluted EPS does not match the company's earnings release. That is an issue. You might also run another team's desk from its README and find that it stops at step 3 with an error. That is an issue too, opened on their repository, with the first line of the error in it.

You will reach for a pull request when you have actual work to hand over for review. Perhaps you rewrote the verifier's prompt and want a teammate to read it before the desk uses it. That is a pull request. Or perhaps a teammate built a rough second seeker and wants the team to consider it. That is also a pull request, because it is a new idea with the code attached.

Once the team has read the pull request, the tests still pass, and everyone agrees, you merge it. Sometimes two of you will have changed the same file. When that happens, Git stops and reports a conflict, which only means it will not choose between your lines for you. Ask your agent to show you both versions and explain the difference, and then you decide.

What to say to your agent

You can tell your agent what to do in plain words, just as you would speak to a colleague.

  • "Open an issue on this repository. The diluted EPS in the latest live report does not match the earnings release. Quote both numbers and where each comes from."
  • "Open an issue on the other team's repository, at this link. Their README stopped at step 3. Here is the first line of the error."
  • "Put my changes on a new branch and open a pull request. In the description, say what I changed and why, in plain words."
  • "Show me the open pull requests and explain what each one changes, in plain words."
  • "My teammates agreed. Merge pull request 4, then update my copy."
  • "There is a merge conflict. Show me both versions and explain the difference. Do not pick one for me."

To open issues and pull requests from the terminal, your agent uses GitHub's own command-line tool, gh, from cli.github.com, which you install and log into once. Your agent can walk you through that setup. Without it, both live on github.com under the Issues tab and the Pull requests tab of the repository, and either way works.

Two cautions

Your repository is public, so every issue and every pull request is public too, which means you must never paste a key or licensed data into one. The clock on a live report is the time of its commit, so commit and push it first, and discuss it afterward.
