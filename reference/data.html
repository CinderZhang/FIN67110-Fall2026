Data — EDGAR, the two required sources, what your reader must return, and the known answers

Finding data and reaching it from code is part of the job. An analyst on any desk learns what the firm pays for and how to pull it, and you learn it the way this course learns everything: ask your AI how to register, where a field lives, how to export, how the Python library opens a session, and check what it tells you against the known answers below. Two sources are required because they are the standards you will meet on a desk and in research; beyond them, use whatever you can get.

Required

Source What it is for here How you get it
SEC EDGAR the filings and the statements as data: the free, public source every desk reads first No account. The ticker-to-CIK file (company_tickers.json), the submissions API for a company's filing list, the documents themselves, and the XBRL company facts (ten-digit CIK), every number with its tag, period and filing. EDGAR requires a User-Agent with your name and email on every request (your .env). Tags differ across filers for the same concept: the Week 2 page shows Walmart's two revenue tags
LSEG Workspace live prices and the latest quarterly fundamentals, the desks' standard (Bloomberg is the other) Register with your Purdue email, following the Libraries' Workspace guide. LSEG approves registrations itself and it can take days: register in Week 1. The Python library (lseg-data) talks to the desktop app; where Purdue's license gives only the web version, its export is the route, and the instructor posts which
WRDS (CRSP, Compustat) history for backtests and base rates, the research standard Request an account with your Purdue email through the Libraries' WRDS guide; the course has a class account if yours is slow. The wrds Python package pulls into code

Also at Purdue: S&P Capital IQ, through the Parrish Library (what it is): company financials, estimates and transactions, reached through its web screens and Excel plug-in rather than a student Python library, so it is an export source. Use it where it has what the two above do not. Anything else that returns the known answers is fine too: the desk does not care where a number came from.

What the reader must return

Three functions, in your own code, for any ticker: the five most recent fiscal quarters reported on or before a date and time (period end, revenue, net income, total debt, cash, in millions); the official daily closes between two dates; the last close before a date and time, a trading day's close being 4:00 PM Eastern. Live, they come from LSEG; for a backtest, the same functions read WRDS. How the code gets them is yours: the vendor's Python library with its key in .env, or a file you exported and keep outside your work folder. Your AI agent writes the reader; your code runs it.

The one rule

Some sources forbid putting their data into AI tools; WRDS says so in its terms. Read the terms of what you use, and where they forbid it, keep the data in code: the desk's design already does that, because the context table is appended to the report by code after the roles have run and no role is shown it. The raw pulls and export files stay out of the repository; the table your code derives travels with the report.

The known answers your reader must reproduce

A close is the exchange's official close for that date; a quarter's revenue is the figure in the 10-Q, 10-K or earnings release that reports it. Before the desk uses your reader, check one close and one quarter it prints against those sources. A source that returns something else (an adjusted close, a standardized field) is telling you what it is; the filing and the exchange decide.
