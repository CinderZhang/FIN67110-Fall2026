Week 5 — One Desk: The Agent Team and the Skills

Mission. On Tuesday, the two things your team built become one desk. You will join the agent team from Week 3 and the skills from Week 4. One command will run them, and the hook will watch every output. On Thursday, you will prove the joined desk on names that nobody on your team chose. You will measure what the join changed, and you will file the team proposal.

Why this matters

You have an agent team that reads filings and writes a verified report. You also have skills that find spinoffs, work one name through a worksheet, and refuse an untraced number. You built these parts separately, but a client wants one thing to run. Joining an agent team to a set of skills is new work. Every agent's documentation describes each part alone. Few public examples show them working together on a task like yours. You have no reference answer this week. Instead, you have a contract, your agent's documentation, and the known answers you already hold. What you learn here is the thing the course is named for.

You arrive with

You arrive with your agent team running on a ticker, plus the seeker, the worksheet, and the hook. You have your first live report filed. You have your team's repository, and you have started the thing you own. You also bring your hand-drawn diagram of the desk as it will run.

Teaching 1 — three ways to join a skill to a team

A skill is a folder of instructions and scripts. Your agent loads the skill when a task matches its description. An agent team is a graph of roles. Each role is a model call with tools, and the team includes a verifier that no run can skip. You can join a skill and an agent team in three ways. One desk may use all three.

The pipeline. The team's run is the skill's input. The team saves a run folder, and the worksheet reads it. Nothing calls anything else. Files on disk are the contract. You already did this in Week 4. The pipeline is the simplest join, and it is the easiest to test because each part runs alone on a saved folder.

The tool. A role calls a skill the same way it calls the filings reader. For example, the Strategy Manager asks the seeker for this week's screen before it assigns work. The Financial Analyst asks the worksheet for the value range before it writes. The skill runs in code and returns a file, and the role reads that file. The role never recomputes a number that the skill computed. Here, the rule that "no model computes a number" earns its keep. The skill's output is data to the role. The verifier checks the role's use of that data just as it checks any quoted line.

The guard. The hook watches both the team and the skill. It runs when the team writes its report and when a skill writes its output. The hook refuses to mark the run "done" if a number has no support from a filing, a facts file, or a printed input.

Your team must choose between the pipeline and the tool, and you must write that design choice down. The pipeline is easier to test and explain. The tool lets a role use the skill's findings inside its own reasoning. A desk that uses the tool also keeps the pipeline, so you can replay a saved run without a model.

Teaching 2 — one command, and the run folder as the contract

A client runs one command. Behind that command, your code fixes the order of the parts, never a model. First, the seeker runs when the client asks for a screen. Next comes the pick, either from the screen or from the ticker the client gave. Then the team runs on that ticker. Next, the worksheet runs on the team's run. The hook runs on every output. Finally, the desk produces the report with the view at the end. Each part writes into one run folder, and the next part reads only from that folder. The first line of the final report names every filing that any part read.

Here is what goes wrong when teams join parts, in the order you will meet each problem:

  • Two parts fetch the same filing twice and get two versions, because the facts file changed between calls. Fetch the filing once, save it, and read from the saved file.
  • A role is handed a skill's output as text and starts recomputing it. Hand the output to the role as a file. Tell the role what it may do with the file: quote it, and never recompute it.
  • The hook reads a file no part wrote. You met this in Week 4's cold run. Make sure the hook reads the saved outputs themselves.
  • The joined desk is slower than the sum, and nobody knows where the delay is. Have each part print the seconds it took on its last line.
  • A name the seeker never saw. The worksheet's spinoff parts print "not applicable", and the rest of the desk runs. The desk does not stop for a company that is not a spinoff. Most companies are not spinoffs.
  • One part fails and the others run on. Stop the command at the part that failed. Print which part failed and the error, and keep the run folder for the replay.

Teaching 3 — measure what the join changed

The honest measure of a join is not that it runs. The honest measure is what the join changed. Take one name and build the three-column table. Column one holds the parts alone, just as Week 4 left them, with the team's verified report and the worksheet's output side by side. Column two holds the joined desk's final report. Column three holds the filing. The rows are the eleven core claims from the audit page, the view, and the one number that decides the view. When a claim differs between the first two columns, check it against the third column. If a join changed nothing, it is a pipeline, and the table says so. If a join changed a number, it is a tool, and the table shows whether the change was right. Put this three-column table in your product manual. The project's reader will look for it.

Teaching 4 — the proposal

Checkpoint 3 is one page: the proposal. It lists the team. It shows the desk's design as one diagram that includes the team, the skills, the hook, and the one command. It includes one paragraph that explains which join the desk uses where. It names the thing the team owns, states each member's role in one line, and shows the live record so far. This proposal is the product manual's first page, and every later draft grows from it.

Three levels

  • Must. One command runs the desk end to end on any ticker; the three-column table on one name; the proposal.
  • Expand. The tool join in one place: the Manager calls the seeker, or the Analyst calls the worksheet, with the role's permission to quote and not to recompute written in its instructions. Or the institution's client: a mandate skill, a file of limits (long only, a cap per name, a cap on all names together, a floor on how much is invested, the benchmark, the fee) and code with no model call that turns the worksheet's views into positions inside the limits and reports the holding week's return against the benchmark, net of fee. A team that serves an institution builds this as the thing it owns, and its product manual compares relative return net of fee against the benchmark.
  • Ship. The desk as a plugin another team installs and runs with one command, with an evaluation that runs the same name with and without each skill.
